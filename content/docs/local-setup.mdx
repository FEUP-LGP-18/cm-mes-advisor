## Recommended Path

Run the full local stack from the workspace root:

```bash
./start.sh
```

The workspace root is one level above the app directory:

```text
/Users/mahmoudali/Documents/LGP project dicovery
```

This is the preferred teammate entrypoint because it handles both the app and the archived support stack.

## What `./start.sh` Does

The root script:

- reads the app Node version from `cm-mes-advisor/.nvmrc`
- expects Node `20.19.0`
- enables Corepack and pnpm
- installs app dependencies only when needed
- safely handles port `3000`
- refuses to kill unrelated processes on required ports
- restarts the archived partner support stack from `98_archive/large-artifacts/LGP2026`
- starts the Next.js app on `http://localhost:3000`

The support stack includes LibreChat, RAG, ClickHouse, FerretDB, and Postgres. Those services support the local partner package; the main app still defaults to mock generation.

## App-Only Fallback

If you only need the Next.js app:

```bash
cd cm-mes-advisor
corepack enable
pnpm install
pnpm dev
```

Then open:

```text
http://localhost:3000
```

Use this path for routine UI and code work when the archived support stack is not needed.

## Supabase Auth Setup

Auth is optional for local mock-only development. To enable Supabase Auth, add
these values to `.env.local` or `.env`:

```text
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your-key-here
```

Leave them unset when you want the app to skip auth entirely for local mock mode.

Only add `SUPABASE_SERVICE_ROLE_KEY` for reviewed server-only admin operations.
Do not expose it through `NEXT_PUBLIC_*`.

## Supabase Migration Workflow

Supabase migrations are stored in `supabase/migrations/`.

Local flow:

```bash
supabase login
supabase link --project-ref <project-ref>
supabase migration new <short_description>
supabase start
supabase db reset
```

Remote flow after review:

```bash
supabase db push
```

See `supabase/README.md` and [Supabase Foundation](/docs/supabase-foundation)
before creating schema migrations.

## Environment Modes

Default:

```text
GENERATION_MODE=mock
```

Mock mode is deterministic and works without partner credentials.

Real mode:

```text
GENERATION_MODE=real
```

Real mode requires server-side configuration. The expected variable names are documented in `.env.example`.

Important real-mode variables include:

- `MCP_SERVER_URL`
- `REQUIREMENT_GENERATION_PROVIDER=bedrock` with `BEDROCK_MODEL_ID`, `AWS_REGION`, and `AWS_BEARER_TOKEN_BEDROCK` or AWS access key credentials
- `REQUIREMENT_GENERATION_PROVIDER=anthropic` with `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL`
- `MCP_USER_ACCOUNT` when the MCP server expects a user account header

Do not copy actual values into docs, commits, prompts, screenshots, or generated exports.

## Common Problems

If port `3000` is already used, prefer the root `./start.sh` because it checks whether the existing process belongs to this app before stopping it.

If real generation is unavailable, first check `GET /api/requirements/generation-availability?refresh=1`. The UI also reads this availability route.

If TypeScript cannot find `collections/server`, run:

```bash
pnpm docs:source
```

That generates the local Fumadocs `.source` folder used by the docs site. The folder is generated and ignored by git.

## What Not To Commit

Never commit:

- `.env` files
- passwords, tokens, API keys, or AWS credentials
- raw partner PDFs or ZIPs
- generated exports
- uploaded workbooks
- extra partner workbooks unless explicitly reviewed
