## Quality Layers

The repo uses several quality layers:

| Layer           | Command                        | Purpose                                        |
| --------------- | ------------------------------ | ---------------------------------------------- |
| ESLint          | `pnpm lint`                    | Static code and Next.js rules                  |
| TypeScript      | `pnpm typecheck`               | No-emit type checking                          |
| Vitest          | `pnpm test`                    | Unit, server, parser, state, and surface tests |
| Next build      | `pnpm build`                   | Production build verification                  |
| Storybook build | `pnpm storybook:build`         | Component/story build verification             |
| Playwright      | `pnpm test:e2e`                | Browser smoke and responsive checks            |
| Full UI review  | `./scripts/codex/review-ui.sh` | Standard frontend verification sequence        |

## Vitest

Config:

```text
vitest.config.ts
```

Vitest includes tests under `src/**/*.test.ts` and `src/**/*.test.tsx`, while excluding Playwright e2e tests.

Main tested areas:

- Excel parser
- source metadata
- workspace state
- project registry
- workflow gating
- generation
- validation
- review actions and storage
- demo script assembly
- Markdown export
- server config/provider/availability
- MCP and Bedrock clients
- API routes
- Phase 1 surfaces

## Playwright

Config:

```text
playwright.config.ts
```

Main spec:

```text
tests/e2e/phase1-smoke.spec.ts
```

The smoke test seeds localStorage with fixture-backed project state and checks major routes across desktop and mobile.

It covers:

- project home
- source
- generate
- review
- script
- export
- dark and light theme paths
- no horizontal overflow
- mobile ordering expectations
- screenshots and artifacts

## Supabase Permission QA

When Supabase credentials and seeded test users are available, run the
multi-user path before calling a release pilot-ready:

- owner creates a project and invites editor/viewer test users
- editor accepts the invite and saves Phase 1 state
- viewer can inspect but cannot upload, review, generate, edit, or save
- editor cannot manage members, invites, archive/delete, or project settings
- non-member direct URLs are denied
- stale save returns a conflict and does not overwrite newer state

If local Supabase credentials or seeded users are unavailable, record that this
path is partially unverified and rely on route/unit tests plus static review for
the server-backed permission boundaries.

## Docs Source Generation

This docs site uses Fumadocs MDX. The generated `.source` folder is ignored by git.

Run manually if needed:

```bash
pnpm docs:source
```

`pnpm typecheck` runs this first so TypeScript can resolve `collections/server`.

## Recommended Verification By Change Type

| Change Type              | Minimum Verification                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| Parser or pipeline logic | `pnpm test`, `pnpm typecheck`                                          |
| Server generation        | relevant server tests, API route tests, `pnpm typecheck`               |
| Route or workflow gating | `pnpm test`, `pnpm test:e2e`                                           |
| UI surface               | `pnpm lint`, `pnpm typecheck`, `pnpm test`, browser desktop/mobile     |
| Docs site                | `pnpm docs:source`, `pnpm typecheck`, `pnpm build`, browser docs check |
| Shared styles            | browser desktop/mobile plus Playwright when practical                  |

## Discovery Caveat

During the original codebase discovery pass, `pnpm test` was started but did not complete before it was stopped. Do not treat that as a passing or failing signal for current work.

When signing off a change, rerun tests and record the actual result.

## CI Expectations

GitHub Actions run the core checks for pull requests. UI changes should still include local browser evidence because CI cannot tell whether the experience is clear or visually coherent.
