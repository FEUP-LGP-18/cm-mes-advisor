## Scope

The collaboration model is project-level, not organization-level. A project is
the access boundary for persisted workbook data, Phase 1 state, future Phase 2
state, files, invites, memberships, and activity.

Schema migration:

```text
supabase/migrations/20260430180000_core_project_collaboration_schema.sql
```

## Tables

The core tables are:

| Table                     | Purpose                                               |
| ------------------------- | ----------------------------------------------------- |
| `projects`                | Project metadata, status, owner-created audit fields  |
| `project_memberships`     | User membership and project role                      |
| `project_invites`         | Invite records for later invite UI/email flows        |
| `project_phase_states`    | Phase-keyed JSON state for Phase 1 and future Phase 2 |
| `project_files`           | Persisted workbook/file metadata and storage path     |
| `project_activity_events` | Project-scoped audit/activity timeline                |

`project_phase_states.phase_key` is intentionally generic so Phase 1 and future
Phase 2 state can coexist without adding one table per workflow step.

Use stable, workflow-level keys rather than route names. Current and reserved
examples:

| Phase key              | Status             | Purpose                                |
| ---------------------- | ------------------ | -------------------------------------- |
| `phase1`               | Current contract   | Phase 1 source/generate/review state   |
| `phase2_master_data`   | Future/reserved    | Phase 2 Master Data setup/review state |

The database check only enforces safe key syntax. It does not hard-code a Phase
1-only enum, so future phase state should use the same `project_phase_states`
table and the same repository helpers.

## Roles

Project roles are stored as the `project_role` enum:

```text
viewer
editor
owner
```

Permission contract:

| Permission area                         | Viewer | Editor | Owner |
| --------------------------------------- | ------ | ------ | ----- |
| Read project metadata                   | Yes    | Yes    | Yes   |
| Read phase state                        | Yes    | Yes    | Yes   |
| Read files                              | Yes    | Yes    | Yes   |
| Read team list                          | Yes    | Yes    | Yes   |
| Upload source workbook / persisted file | No     | Yes    | Yes   |
| Save phase state                        | No     | Yes    | Yes   |
| Edit project settings                   | No     | No     | Yes   |
| Manage members and invites              | No     | No     | Yes   |
| Archive/delete project                  | No     | No     | Yes   |

## RLS Helpers

The migration defines security-definer helper functions so policies can check
membership without recursive RLS reads:

```text
current_project_role(project_id)
can_view_project(project_id)
can_edit_project(project_id)
can_manage_project(project_id)
```

Use the same meanings in server-side repository code:

- `can_view_project`: any member
- `can_edit_project`: `editor` or `owner`
- `can_manage_project`: `owner`

## RLS Contract

RLS is enabled on every project table.

Non-members cannot read or mutate project rows directly.

Members can read:

- project metadata
- phase state
- files
- team list
- activity events

Editors and owners can insert/update phase state and upload file metadata.

Owners can:

- update project metadata/status
- delete projects
- add, update, and remove memberships
- create, update, revoke, and delete invites
- delete files and phase state records

## Server Route Contract

Server routes must go through the project permission and repository layer rather
than calling Supabase tables directly. The repository still relies on RLS as the
database authority; route code should use the helper result types to fail closed
before doing domain work.

Future Phase 2 routes should follow this shape:

```ts
const user = await requireProjectCapability(projectId, "edit_project_state");
if (!user.ok) {
  return NextResponse.json({ ok: false, error: user.message }, { status: 403 });
}

const result = await saveProjectPhaseState(
  projectId,
  "phase2_master_data",
  state,
  expectedVersion,
  user.data.id,
);
```

Use `getProjectPhaseStateForUser(projectId, "phase2_master_data", userId)` for
reads and `saveProjectPhaseState(projectId, "phase2_master_data", ...)` for
writes. Do not add a Phase-2-specific persistence table unless the data model
requires relational queries that JSON phase state cannot support.

Suggested Phase 2 capability mapping:

| Future Phase 2 action                  | Capability                  | Role effect       |
| -------------------------------------- | --------------------------- | ----------------- |
| Read Master Data setup/review/export   | `read_project`              | Viewer and above  |
| Generate Master Data draft             | `edit_project_state`        | Editor and owner  |
| Edit/approve Master Data objects       | `edit_project_state`        | Editor and owner  |
| Download generated export package      | `read_project` by default   | Viewer and above  |
| Upload supporting project files        | `upload_project_file`       | Editor and owner  |
| Manage project/team/settings           | `manage_project_settings` or `manage_project_members` | Owner |
| Archive/delete project                 | `archive_project` or `delete_project` | Owner |

If the product later decides generated export packages should be restricted to
editors, use `edit_project_state` for that route. The current default is
viewer-plus read access for generated downloads.

## Owner Safety

Every project gets an initial owner membership from `projects.created_by`.

The database blocks deleting or demoting the last owner through
`prevent_last_project_owner_removal()`. To transfer ownership, add or promote a
second owner first, then demote/remove the previous owner.

Project deletion is still allowed for owners; the last-owner guard skips child
membership rows removed by project cascade delete.

## Audit Fields

Triggers populate or update audit fields from `auth.uid()` where possible:

- `projects.created_by`
- `projects.updated_by`
- `project_phase_states.updated_by`
- `project_files.uploaded_by`
- `project_activity_events.actor_id`

Repository code should still pass explicit user context and validate intended
actions before writing. RLS is the final database boundary, not the whole
application permission layer.
