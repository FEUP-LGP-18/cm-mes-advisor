## Deployment Model

The production deployment path is Vercel Git Integration connected to the GitHub repo.

Production deployments run from the `main` branch. Preview deployments are created from pull requests or non-production branches when the Vercel project is connected to GitHub.

The app is configured to keep Vercel builds safe with mock generation by default.

## GitHub And Vercel Files

- `.github/workflows/ci.yml`: pull request lint, typecheck, tests, build, Storybook build, and Playwright smoke.
- `.github/workflows/vercel-preview.yml`: token-based Vercel preview fallback for PRs.
- `.github/workflows/vercel-production.yml`: token-based Vercel production fallback from `main`.
- `.vercel/project.json`: local Vercel project link. Keep `.vercel/` out of commits.

The Vercel workflow files skip gracefully when required token secrets are not configured. They are not the primary deployment path when Vercel Git Integration is connected.

## Vercel Git Integration

The expected production setup is:

- Vercel project: `cm-mes-advisor`
- GitHub repo: `FEUP-LGP-18/cm-mes-advisor`
- production branch: `main`
- root directory: `.`

After Git Integration is connected, pushing `main` triggers the production deployment in Vercel.

## Optional GitHub Actions Secrets

The token-based workflow fallback needs these GitHub repository secrets:

- `VERCEL_TOKEN`
- `VERCEL_ORG_ID`
- `VERCEL_PROJECT_ID`

Do not commit these values. Do not paste them into docs, issue comments, screenshots, prompts, or generated exports.

## Environment Policy

Vercel preview and production are expected to use:

```text
GENERATION_MODE=mock
NEXT_PUBLIC_SUPABASE_URL=<Supabase project URL>
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<Supabase publishable key>
```

This keeps review deployments usable without partner credentials.

Real mode should only be enabled when server-side MCP plus the selected model-provider credentials are available and the team intentionally wants to validate that path.

Supported requirement-generation providers are:

- `REQUIREMENT_GENERATION_PROVIDER=bedrock`
- `REQUIREMENT_GENERATION_PROVIDER=anthropic`

For Anthropic validation, configure `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` only as Vercel environment variables. Do not paste secret values into PRs, docs, screenshots, or workflow files.

For strict Vercel smoke validation with Anthropic, the target Vercel environment needs:

```text
GENERATION_MODE=real
REQUIREMENT_GENERATION_PROVIDER=anthropic
MCP_SERVER_URL=self
ANTHROPIC_API_KEY=<server-side secret>
ANTHROPIC_MODEL=<Anthropic model>
AI_SMOKE_TEST_TOKEN=<server-side smoke token>
```

`MCP_SERVER_URL=self` uses the app-hosted MCP documentation endpoint at
`/api/requirements/mcp`. This is the preferred Vercel value because it works on
Preview and Production without exposing a local MCP/RAG service to the public
internet. External MCP server URLs remain supported when a partner-hosted MCP
endpoint is available.

After the preview or production URL is deployed, run:

```bash
AI_SMOKE_URL=https://<vercel-deployment-url> pnpm smoke:ai:vercel
```

If deployment protection is enabled, include the local-only Vercel automation bypass secret:

```bash
VERCEL_PROTECTION_BYPASS=<automation bypass secret> \
  AI_SMOKE_URL=https://<vercel-deployment-url> \
  pnpm smoke:ai:vercel
```

If you specifically need to validate the archived local MCP/RAG Docker stack on
port `8080` from Vercel Preview, use the temporary tunnel helper with the local
support stack running and `cloudflared` installed:

```bash
pnpm vercel:mcp:tunnel
```

That command starts a Cloudflare quick tunnel to local MCP/RAG, updates only the
Vercel Preview `MCP_SERVER_URL`, deploys a Preview build, and runs
`pnpm smoke:ai:vercel`. It does not print the tunnel URL, `MCP_SERVER_URL`,
smoke token, Vercel bypass secret, API keys, or generated text.

The quick tunnel is an operational bridge for the archived local RAG stack only.
Stable production should use `MCP_SERVER_URL=self` or a persistent partner MCP
URL.

Production cannot validate this Anthropic provider until the provider code is merged into `main` or otherwise deployed to the production Vercel project.

## Supabase Deployment Setup

Before a Supabase-backed preview or production release:

1. Apply reviewed migrations with `supabase db push`.
2. Confirm `profiles`, project collaboration tables, storage bucket policies, and RLS are present.
3. Configure Supabase Auth email/password providers and set the Auth Site URL to the production app URL.
4. Add redirect URLs for local, preview, and production callback paths:
   `http://localhost:3000/auth/callback`,
   `https://*-<vercel-team-or-account-slug>.vercel.app/**`, and
   `https://<production-domain>/auth/callback`.
5. Set Vercel Production `NEXT_PUBLIC_SITE_URL` to the production app URL so email redirects use the canonical domain after deployment.
6. Confirm email templates use Supabase's confirmation URL variable rather than a hard-coded localhost or Site URL link.
7. Keep `SUPABASE_SERVICE_ROLE_KEY` unset unless a reviewed server-only admin task needs it.
8. Verify the private `project-files` bucket exists and that workbook uploads are not public.

Do not expose Supabase secret values in `/settings`, docs, screenshots, issue comments, or generated exports. The global settings page should only show safe configured/not-configured indicators.

## Pull Request Flow

Expected PR behavior:

1. CI validates code and build health.
2. Vercel Git Integration creates a preview deployment when connected.
3. The token-based preview workflow can also comment a preview URL when its secrets exist.
4. Reviewers use the preview plus local evidence for UI and workflow checks.

## Production Flow

Pushes to `main` trigger Vercel production through Git Integration. Production should not require partner credentials while the app remains in mock mode.

## What CI Does Not Prove

CI can prove that commands pass. It cannot prove:

- the UI is clear
- mobile hierarchy is good
- next-action language is coherent
- a consultant can understand the workflow
- real Bedrock or Anthropic access is validated in the target runtime

For UI-heavy changes, include browser verification notes even when CI is green.

## Build And Docs Interaction

The docs site is built as part of the Next.js app. Fumadocs generates `.source` during docs source generation and build.

If build or typecheck fails with missing docs collection imports, run:

```bash
pnpm docs:source
```

Then rerun:

```bash
pnpm typecheck
pnpm build
```

## Deployment Safety Rules

- Keep raw partner artifacts out of commits.
- Keep generated exports out of commits.
- Keep credentials server-side only.
- Keep `GENERATION_MODE=mock` for review deployments unless the team explicitly switches modes.
- Stage files explicitly so local duplicate `* 2` files, `.source`, `.vercel`, test artifacts, and `.env` files do not slip into commits.
- Do not mark real mode complete without a new validation record.
